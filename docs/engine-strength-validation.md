# Stockfish 原生限强验证

日期：2026-11-20。本文记录针对 0.4.3 的方案一独立实验，实验当时未修改应用的六档难度、提示、存档或 APK。后续 0.4.4 已接入原生限强，实际参数见 [架构与规则](architecture.md#难度与提示)；以下保留实验过程与观察。

## 结论

- 当前随包引擎支持原生限强，能够从合理候选中选择非最优着法，适合替代全部合法走法等概率随机的对战策略。
- 不能据此认定最低档适合需求中的约 Elo 100 初学者。Skill 0 即使只搜索深度 1，也在本次样本中全部找到一步将杀、全部避开对方的一步将杀；面对明显战术机会仍然很敏锐。
- 低档仍有不自然的失误：换子后有时不回吃，反而走兵。因此「比随机更有棋理」不等于「已模拟人类新手」。
- 本次没有测得 Elo，不添加分数标签，也不据此确定正式六档参数。

## 方法与复现

在仓库根目录执行：

```sh
node scripts/verify-engine-strength.mjs
```

依赖已安装的 `chess.js` 和 `public/engine/` 中的引擎资源。资源缺失时先执行 `npm run prepare:assets`。

脚本把随包的 JS / WASM 原样复制至临时目录，以 `.cjs` 扩展名调用同一 JS 文件自带的 Node CLI；不下载或替换引擎，不改源文件内容。进程与临时目录在结束时清理，逐次样本写入被 Git 忽略的 `artifacts/engine-strength-validation.json`。

实际引擎自报 `Stockfish 19 Lite WASM`，`Skill Level=0–20`、`UCI_Elo=1320–3190`。本次使用 Node v22.23.5；不是浏览器或 Android WebView 验收。

七个局面全部从标准初始局面按合法棋谱生成：开局、出子阶段、白送皇后、一步将杀、防一步将杀、换子回吃、开局陷阱。具体棋谱与 FEN 保存在脚本和原始结果中。

| 测试配置 | 最大深度 | 搜索时间上限 | 每个局面取样数 |
| --- | --- | --- | --- |
| Skill 0 | 1 | 50 ms | 20 |
| Skill 0 / 5 / 10 / 20，各自独立取样 | 8 | 200 ms | 各 20 |

每轮共 700 次选择，另对七个局面各做一次不限强、全合法走法 MultiPV 参考分析，深度上限 10、时间上限 1500 ms；本次连续执行两轮，合计 1400 次选择，参考分析均达到深度 10。下表及原始 JSON 对应最后一轮；再次执行脚本会覆盖该 JSON。参考评分只用于比较局面中的走法，不是绝对正确性证明或 Elo 换算。

每次搜索前发送 `ucinewgame`，固定 `Hash=16`，关闭 `UCI_LimitStrength`，避免其覆盖 Skill Level。不同 Skill 使用相同深度和时间限制以便比较。额外的 Skill 0 / 深度 1 用来检查进一步减少搜索是否足够。

对战选择读取最终 `bestmove`；两轮全部返回走法均通过 `chess.js` 合法性校验。一步将杀和防杀直接用棋规枚举验证，不以引擎评分代替；吃后、回吃直接检查实际捕获棋子。随机列是 0.4.3 最低档均匀选择的精确概率，不是另做的 20 次随机取样。

## 本次结果

以下次数均为对应局面 20 次取样中的成功次数，随机列为单步成功概率。

| 局面与判定 | 0.4.3 完全随机 | Skill 0 / 深度 1 | Skill 0 / 深度 8 | Skill 5 / 深度 8 | Skill 10 / 深度 8 | Skill 20 / 深度 8 |
| --- | --- | --- | --- | --- | --- | --- |
| 吃掉白送的皇后 | 1/32，3.1% | 18/20 | 19/20 | 20/20 | 20/20 | 20/20 |
| 立即一步将杀 | 1/43，2.3% | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 |
| 不允许对方下一步将杀 | 8/28，28.6% | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 |
| 换子后立即回吃对方的象 | 2/26，7.7% | 11/20 | 18/20 | 20/20 | 20/20 | 20/20 |

开局 `1.e4` 之后，Skill 0 的两个搜索预算都只选出 `e5`、`c5`、`e6`、`Nc6` 四种回应；不再从全部 20 个合法走法随意选择。出子局面中，Skill 0 / 深度 8 选择 `O-O`、`Nd5`、`Bg5`、`h3`，表现出基本棋理。这是少量局面的观察，不能推广为所有开局都自然。

不自然的例子：最后一轮换子局面中，Skill 0 / 深度 8 有 2/20 次不回吃，分别走 `h5`、`Nf6`；深度 1 有 9/20 次不回吃。第一轮两个预算各有 7/20 次不回吃。降低搜索深度未消除这个现象，具体频次受随机取样影响。

## 接入时必须处理的差异

0.4.3 的 `src/engine.ts` 在收到 `bestmove` 时，只把它当作搜索结束信号，实际返回最深完整分析中的候选；`src/App.tsx` 取第一个候选走棋。0.4.4 已将对战与提示的返回结果区分处理。

实测最终 `bestmove` 与最深分析第一候选不同的次数：

| 配置 | 不同次数 / 全部取样 |
| --- | --- |
| Skill 0 / 深度 1 | 65/140 |
| Skill 0 / 深度 8 | 64/140 |
| Skill 5 / 深度 8 | 53/140 |
| Skill 10 / 深度 8 | 59/140 |
| Skill 20 / 深度 8 | 0/140 |

因此不能只在现有 `analyze()` 中增加 Skill 参数。正式接入需要让对战使用引擎最终的合法 `bestmove`，提示仍使用不限强的 MultiPV 分析；否则会在上述样本中覆盖引擎刻意选出的弱着。

## 性能与边界

- 本机预热后，Skill 0 / 深度 8 平均每次搜索约 4–26 ms，各局面最大值不超过 26 ms；Skill 0 / 深度 1 的单次值四舍五入到毫秒后为 0。这不是整个应用的响应耗时。
- 总耗时约 9 秒，含本次引擎初始化、参考分析及 700 次选择。应用原有的 500 ms 落子等待不在实验中。
- 实验复用一个引擎进程，应用每次请求创建新 Worker；本次独立实验没有验证冷启动、取消、手机或平板耗时。0.4.4 的集成验收另见测试记录。
- 使用引擎自身随机数，不固定种子；重跑应得到相似现象，但具体频次可能变化。20 次全部成功不代表真实成功概率必为 100%。
- 局面数量少且包含多个人为设置的明显机会，未做完整对局、人类新手盲测或棋力标定，不能断言档位严格单调，也不能推断相当于某个平台 Elo。

建议：方案一在技术上可行，可以作为「去掉完全随机」的最小改动；但对约 Elo 100 的目标使用者，只能作为待试玩的候选，不应仅凭原生最低档就宣布新手难度已合适。若试玩仍过强，再考虑方案二，不在本次实验中扩展实现。
